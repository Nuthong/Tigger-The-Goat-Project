Infrastructure — ทำเมื่อไหร่ และทำไม (When / Why)

วางรากฐานก่อนเขียนฟีเจอร์แม้แต่บรรทัดเดียว

  • When — ตั้ง docker-compose.yml ตั้งแต่ต้น ก่อน backend/frontend จะมี endpoint จริงด้วยซ้ำ เพื่อให้ทุกคนในทีมรันสภาพแวดล้อมเดียวกันได้ทันทีตั้งแต่วันแรก
  • Why — reproducible: "งานที่เครื่องฉันรันได้" ใช้ไม่ได้กับทีม 6 คน — Docker การันตีว่า PostgreSQL/Python/Node เป็นเวอร์ชันเดียวกันเป๊ะทุกเครื่อง
  • Why — dev/prod parity: คอนเทนเนอร์ชุดเดียวกับที่รัน local คือของที่จะขึ้น production จริง ไม่ต้องเขียนโค้ดสองชุด
  • Why — isolation: ฐานข้อมูลทดสอบพังได้ ลบทิ้งสร้างใหม่ได้ทุกเมื่อ ไม่กระทบเครื่องคนอื่นในทีม

Infrastructure — ทำงานอย่างไร (How) · รายละเอียดใน docker-compose.yml

ไม่ใช่แค่ "รันแล้วหวังว่าจะติด"

  • Healthcheck ต่อกันเป็นห่วงโซ่ — api รอจน db ตอบ pg_isready ก่อนถึงจะเริ่ม (depends_on: condition: service_healthy) แล้ว web ก็รอ api ให้ /health ตอบ 200 ก่อนเช่นกัน — กัน race condition ตอน "ขึ้นพร้อมกัน" ไม่ใช่แค่ "สั่งพร้อมกัน"
  • จำกัดทรัพยากรต่อ container — db 512MB · api 512MB/1 CPU · web 256MB/0.5 CPU — คิดเรื่อง capacity ไว้ตั้งแต่ตอน dev ไม่ใช่มาคิดตอน production พัง
  • Volume ชื่อ pgdata เก็บข้อมูล PostgreSQL แยกจากตัว container — ลบ/สร้าง container ใหม่ได้โดยข้อมูลไม่หาย (ต้องลบ volume เองถึงจะล้างข้อมูลจริง)
  • ค่าเริ่มต้นปลอดภัยไว้ก่อน — รหัสผ่าน/secret ทุกตัวมี default (เช่น ${JWT_SECRET:-local-demo-secret...}) ให้ docker compose up ใช้ได้ทันทีโดยไม่ต้องตั้งค่าอะไรก่อน แต่ override ได้ผ่านไฟล์ .env (git-ignored) ตอนจะขึ้น production จริง

Infrastructure — ทำงานอย่างไร (How) · nginx ทำอะไรมากกว่า proxy

ประตูหน้าบ้านที่ทำงานหนักกว่าที่คิด

  • ใส่ security header เอง (CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy) — ป้องกันตั้งแต่ ก่อนคำขอจะถึง React ด้วยซ้ำ
  • แคช asset ที่ build แล้ว (/assets/*, ฟอนต์) แบบ immutable 1 ปี — เพราะไฟล์พวกนี้มีชื่อ hash ต่อท้าย เปลี่ยนโค้ดแล้ว build ใหม่ ชื่อไฟล์จะเปลี่ยนเองโดยอัตโนมัติ
  • วิดีโอ hero ใช้ no-cache (ไม่ใช่ไม่แคช แค่ต้อง revalidate ทุกครั้ง) เพราะชื่อไฟล์คงที่แต่เนื้อหา อาจถูกเปลี่ยนได้
  • try_files $uri /index.html — กด refresh หน้า /admin/bookings/42 ตรง ๆ แล้วไม่เจอ 404 เพราะ React Router (client-side) เป็นคนจัดการ route จริง ไม่ใช่ nginx

Database — ทำเมื่อไหร่ และทำไม (When / Why)

ออกแบบก่อนเขียนโค้ดสักบรรทัด แล้วล็อกไว้

  • When — ผ่าน 3 ขั้น conceptual (ER model) → logical (normalization) → physical (DDL จริง) ก่อน backend จะเริ่มเขียน model ใด ๆ เลย เสร็จแล้ว "ล็อก" ไม่ให้แก้อีกตลอดการพัฒนา
  • Why lock — กัน schema drift: ทุกคนในทีมเขียนโค้ดอ้างอิงโครงสร้างเดียวกันตลอด ไม่ต้อง migrate ข้อมูลเก่าไปมา
  • Why normalize (1NF→3NF) — ไม่เก็บข้อมูลซ้ำ (ยกเว้นตั้งใจ เช่น ราคา snapshot ตอนจอง) → แก้ข้อมูลที่เดียว ถูกทุกที่ ไม่มี update anomaly
  • Why constraint-first — กติกาธุรกิจ (เช่น "ห้ามจองห้องซ้อนกัน") ฝังไว้ที่ฐานข้อมูลเป็นด่านสุดท้าย แม้โค้ด backend จะมีบั๊กก็ยังกันได้

Backend — ทำเมื่อไหร่ และทำไม (When / Why)

สร้างทีละชั้น เริ่มจาก auth

  • When — เริ่มหลัง schema ล็อกเสร็จ ทำ auth ก่อน (ทุกอย่างต้องมี login) ตามด้วย rooms/bookings (แกนหลักของระบบ) แล้วค่อยขยายเป็นโมดูล ops (housekeeping/maintenance/invoices/rate-plans) ใน Draft 2
  • Why layered — แยก "โครงสร้างข้อมูล" (models) ออกจาก "กติกาธุรกิจ" (services) ออกจาก "ทางเข้า HTTP" (api) แก้ตรงไหนก็ไม่กระทบชั้นอื่นโดยไม่ตั้งใจ
  • Why async — รับหลายคำขอพร้อมกันได้โดยไม่บล็อก เหมาะกับงานที่รอ I/O เยอะอย่างระบบจอง
  • Why RBAC 6 role — พนักงานแต่ละแผนกเห็น/ทำได้ไม่เท่ากัน (แม่บ้านไม่เห็นรายงานการเงิน, บัญชีเปลี่ยนสถานะห้องไม่ได้)

Backend — ทำงานอย่างไร (How)

1 คำขอ เดินผ่าน 4 ด่าน

  • 1 — Middleware ตรวจ JWT access token จาก header → รู้ว่าใครเรียก role อะไร
  • 2 — FastAPI dependency require_role(...) เช็คสิทธิ์ก่อนเข้า route — ไม่ผ่านคืน 403 ทันที
  • 3 — Route เรียก service function (ตรรกะธุรกิจ) → service คุย DB ผ่าน SQLAlchemy (async)
  • 4 — ผลลัพธ์ผ่าน Pydantic schema (*Out) แปลงเป็น JSON — ฟิลด์ที่ไม่อยากให้เห็นจะไม่หลุดออกไปเอง

ตัวอย่าง IDOR guard: booking ที่เป็นของลูกค้าคนอื่น → ตอบ 404 ไม่ใช่ 403 (ไม่บอกด้วยซ้ำว่า resource นั้นมีอยู่จริง)

Frontend — ทำงานอย่างไร (How)

เรียก API ยังไง จำ token ตรงไหน

  • lib/api.ts — fetch client กลางตัวเดียว ทุกหน้าเรียกผ่านนี้ ไม่มี fetch กระจัดกระจาย
  • Access token — เก็บในหน่วยความจำ (ไม่ใช่ localStorage) กัน XSS ขโมย token
  • Refresh token — httpOnly cookie ต่ออายุ session แบบเงียบ ๆ เมื่อ access token หมดอายุ
  • Component ใช้ร่วมกัน — <Pager> <EmptyState> <TableEmpty> <FilterPanel> ใช้ซ้ำได้ทุกตารางในพอร์ทัลแอดมิน
  • ดีไซน์: display type ตัวใหญ่ ปุ่ม pill · section สลับขาว/เทา/ดำ · accessibility (focus ring, label ครบ, aria-live toast, reduced-motion)

Frontend — ทำงานอย่างไร (How) · Routing & สิทธิ์การเข้าถึง

กันสิทธิ์ 2 ชั้น ไม่ใช่เชื่อ backend อย่างเดียว

  • <GuestRoute> ครอบหน้าลูกค้าทุกหน้า — ถ้า staff ล็อกอินแล้วหลงเข้าหน้าลูกค้า จะถูกเด้งไปพอร์ทัลแอดมินทันที
  • <ProtectedRoute> ครอบทุก route ใต้ /admin/* พร้อมระบุ require="staff" / "manager" / "frontdesk" เจาะจงเป็นหน้า ๆ ไป — พิมพ์ URL admin ตรง ๆ โดยไม่มีสิทธิ์ก็เข้าไม่ได้
  • route ที่ต้องล็อกอิน (เช่น /bookings, /book/confirm) ครอบด้วย <ProtectedRoute> เปล่า ๆ (แค่เช็คว่าล็อกอินหรือยัง ไม่เช็ค role)
  • นี่คือ UX เท่านั้น — ด่านจริงที่ป้องกันข้อมูลคือ backend RBAC (ดูสไลด์ Backend Security) ฝั่ง frontend แค่ไม่ให้ผู้ใช้เดินไปเจอหน้าที่กดอะไรไม่ได้อยู่ดี

Deployment — ทำเมื่อไหร่ และทำไม (When / Why)

รันบนเครื่อง local ทุกวันตั้งแต่ต้น

  • When — สแตก Docker รันอยู่บนเครื่อง dev มาตั้งแต่ Infrastructure ถูกวางในวันแรก ๆ ใช้ทดสอบทุกฟีเจอร์ ก่อนส่งงานแต่ละรอบ — ยังไม่ได้ขึ้นคลาวด์จริงในตอนนี้
  • Why local-first — ทดสอบ/แก้บั๊กได้เร็วกว่า ไม่ต้องรอ deploy ทุกครั้งที่แก้โค้ด ไม่มีค่าใช้จ่ายระหว่างพัฒนา
  • Why คลาวด์เป็นขั้นต่อไป — เอกสาร DEPLOY.md เตรียมไว้แล้ว (Neon/Render/Vercel) พร้อมขึ้นทันที ที่ทีมพร้อม โดยใช้ container ชุดเดียวกับที่รัน local — ไม่ต้องเขียนใหม่

Deployment — ทำงานอย่างไร (How)

คำสั่งเดียวได้ทั้งสแตก

cd 06-deploy && docker compose up --build -d && ./load-db.sh

  • สร้าง 3 container พร้อมกัน (db/api/web) ต่อ network เดียวกันให้อัตโนมัติ
  • load-db.sh โหลด schema → roles → seed เข้า PostgreSQL ให้เอง ไม่ต้องรันมือทีละไฟล์
  • เปิด http://localhost:8081 ใช้งานได้ทันที ไม่ต้องตั้งค่าอะไรเพิ่ม

Deployment — ทำงานอย่างไร (How) · ทำไมสั่งครั้งเดียวถึงพอ

ลำดับที่ Docker จัดการให้อัตโนมัติ

  • 1 — db เริ่มก่อน รอจน pg_isready ตอบ "พร้อม" (ไม่ใช่แค่ container ติดแล้ว — PostgreSQL อาจยังโหลดไม่เสร็จ)
  • 2 — api เริ่มก็ต่อเมื่อ db healthy แล้วเท่านั้น รอจน /health ตอบ 200
  • 3 — web เริ่มก็ต่อเมื่อ api healthy แล้ว — build React แล้ว serve ผ่าน nginx
  • 4 — load-db.sh รันแยกอีกที (ไม่ auto) เพื่อโหลด schema/roles/seed — แยกจาก "container ติด" เพราะ DB เปล่า ๆ กับ DB มีข้อมูลแล้ว เป็นคนละสถานะกัน

ขั้นต่อไปที่ยังไม่ทำ: ย้าย 3 ข้อบนไปรันบน Neon (DB) + Render (API) + Vercel (Web) จริง — ขั้นตอน/env var เดียวกันนี้ เอกสารไว้ครบใน 06-deploy/DEPLOY.md

เชื่อมทุกชั้นเข้าด้วยกัน

ตัวอย่างจริง: กดปุ่ม "จองห้อง" 1 ครั้ง เกิดอะไรขึ้นบ้าง

  • Frontend — ConfirmReservation.tsx เรียก bookings.create() ใน lib/api.ts → POST /api/v1/bookings พร้อม JWT ใน header
  • Infrastructure — nginx เห็น path ขึ้นต้นด้วย /api → proxy ไปที่ container api:8000
  • Backend — middleware ตรวจ JWT → require_role ผ่าน (customer) → route เรียก booking_service.create_booking()
  • Database — service สั่ง INSERT เข้า booking + booking_room → trigger bi_booking_room_no_overlap เช็คห้องไม่ซ้อนก่อน commit — ถ้าชนคืน error ทันที ไม่ต้องรอ backend เช็คเอง
  • กลับทาง — response วิ่งย้อน Database → Backend → nginx → Frontend หน้าจอแสดงเลขที่การจอง (TIG-00042) ให้ลูกค้าเห็นภายในไม่กี่ร้อย ms
