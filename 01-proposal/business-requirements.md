## 1. บทนำ

### 1.1 วัตถุประสงค์ของเอกสาร

เอกสารฉบับนี้กำหนดความต้องการทางธุรกิจของระบบจองห้องพักและบริหารงานโรงแรม เพื่อใช้เป็นข้อตกลงร่วมระหว่างผู้มีส่วนได้ส่วนเสียว่าระบบต้องจัดเก็บข้อมูลใด ต้องบังคับใช้กฎทางธุรกิจใด และต้องให้บริการผู้ใช้แต่ละบทบาทอย่างไร ข้อกำหนดทุกข้อในเอกสารนี้สอดคล้องกับฐานข้อมูลที่ส่งมอบ (`03-database/schema.sql`) และสามารถตรวจสอบย้อนกลับไปยังตาราง ข้อจำกัด (constraint) วิว ฟังก์ชัน หรือทริกเกอร์ที่บังคับใช้ได้

### 1.2 ขอบเขตของเอกสาร

เอกสารนี้ครอบคลุมความต้องการทางธุรกิจ กฎทางธุรกิจ ความต้องการด้านข้อมูล และความต้องการที่ไม่ใช่เชิงหน้าที่ของระบบ ทั้งส่วนเว็บไซต์สำหรับลูกค้าและส่วนงานสำหรับพนักงาน (Staff Portal) รายละเอียดการออกแบบเชิงเทคนิคของแต่ละตารางอยู่ในเอกสาร Relational Schema และ ER Diagram ในโฟลเดอร์ `02-design/`

### 1.3 กลุ่มผู้อ่าน

อาจารย์ผู้สอนรายวิชา สมาชิกกลุ่มผู้พัฒนา และผู้ใช้งานระบบในแต่ละบทบาท ได้แก่ ผู้จัดการโรงแรม พนักงานต้อนรับส่วนหน้า พนักงานแม่บ้าน พนักงานบัญชี และผู้ดูแลระบบ

### 1.4 นิยามศัพท์

| คำศัพท์ | ความหมาย |
|---|---|
| การจอง (Booking) | รายการเข้าพักหนึ่งครั้งของลูกค้าหนึ่งคน ประกอบด้วยช่วงวันที่ ห้องพักอย่างน้อยหนึ่งห้อง และบริการเสริม (ถ้ามี) |
| คืนที่เข้าพัก (Night) | จำนวนวันระหว่างวันเช็คอินถึงวันเช็คเอาท์ โดยไม่นับคืนของวันเช็คเอาท์ |
| โฟลิโอ (Folio) | ใบสรุปค่าใช้จ่ายทั้งหมดของการจองหนึ่งรายการ ได้แก่ ค่าห้องและค่าบริการเสริม |
| แผนราคา (Rate Plan) | ราคาต่อคืนที่ใช้แทนราคาตั้งต้นของประเภทห้องในช่วงวันที่กำหนด เช่น ราคาตามฤดูกาล วันธรรมดา วันหยุดสุดสัปดาห์ หรือโปรโมชัน |
| ราคาตั้งต้น (Base Price / List Price) | `room_type.base_price_per_night` ใช้เมื่อไม่มีแผนราคาใดครอบคลุมคืนนั้น |
| การล็อกราคา (Price Snapshot) | การคัดลอกราคา ณ เวลาที่ทำรายการไปเก็บในรายการจอง เพื่อไม่ให้ยอดเงินเปลี่ยนตามราคาปัจจุบัน |
| การกันห้องชั่วคราว (Hold) | การจองออนไลน์สถานะ `pending` ที่ยังไม่ชำระเงิน ระบบกันห้องไว้ให้ในเวลาที่กำหนด |
| ไม่มาเข้าพัก (No-show) | การจองที่ยืนยันแล้วแต่ลูกค้าไม่มาเช็คอินจนเลยวันเข้าพัก |
| ใบแจ้งหนี้ / ใบกำกับภาษี (Invoice) | เอกสารแสดงยอดที่เรียกเก็บของการจอง พร้อมภาษีมูลค่าเพิ่ม แยกจากการชำระเงิน |
| วิว (View) | ตารางเสมือนที่ประกอบจากคำสั่ง SELECT ใช้คำนวณข้อมูลสรุปโดยไม่จัดเก็บซ้ำ |
| ทริกเกอร์ (Trigger) | กลไกของฐานข้อมูลที่ทำงานอัตโนมัติเมื่อมีการเพิ่มหรือแก้ไขข้อมูล |
| RBAC | การควบคุมสิทธิ์ตามบทบาทผู้ใช้ (Role-Based Access Control) |
| Audit Trail | บันทึกประวัติการทำงานที่ระบุผู้กระทำ การกระทำ ข้อมูลที่ถูกกระทำ และเวลา |

### 1.5 ข้อตกลงในการอ่านเอกสาร

- รหัส **BO-n** หมายถึงวัตถุประสงค์ทางธุรกิจ, **FR-n** หมายถึงความต้องการเชิงหน้าที่, **BR-n** หมายถึงกฎทางธุรกิจ, **DR-n** หมายถึงความต้องการด้านข้อมูล และ **NFR-n** หมายถึงความต้องการที่ไม่ใช่เชิงหน้าที่
- เลขกฎทางธุรกิจในเอกสารนี้ใช้ชุดเดียวกับที่อ้างอิงไว้ในความเห็น (comment) ของ `schema.sql` ได้แก่ BR-3, BR-5, BR-6, BR-9 และ BR-11 เอกสารนี้จึงเป็นรายการกฎทางธุรกิจฉบับอ้างอิงของโครงการ
- คำว่า "ต้อง" หมายถึงข้อกำหนดบังคับ ส่วนคำว่า "ควร" หมายถึงข้อกำหนดที่แนะนำ
- ชื่อตาราง คอลัมน์ และค่าข้อมูลแสดงด้วยอักษรแบบโค้ด เช่น `booking.status`

## 2. ภาพรวมทางธุรกิจ

### 2.1 สภาพปัจจุบันและปัญหา

โรงแรมขนาดกลางย่านใจกลางกรุงเทพมหานคร จำนวน 155 ห้อง 9 ชั้น 5 ประเภทห้อง บันทึกการจองด้วยสมุดและตารางคำนวณ ทำให้เกิดปัญหาดังนี้

1. การจองห้องซ้ำซ้อนในช่วงวันเดียวกัน (double booking)
2. การค้นหาห้องว่างตามช่วงวันใช้เวลานานและไม่แม่นยำ
3. ยอดเงินของแต่ละการจองคำนวณด้วยมือ เกิดความคลาดเคลื่อนเมื่อมีการชำระหลายงวดหรือคืนเงิน
4. ราคาห้องเปลี่ยนตามฤดูกาลและวันในสัปดาห์ แต่ไม่มีหลักฐานว่าลูกค้าแต่ละรายได้รับราคาใด
5. งานทำความสะอาดหลังเช็คเอาท์และงานแจ้งซ่อมตกหล่น ห้องที่ยังไม่พร้อมถูกขายซ้ำ
6. สรุปรายได้และอัตราการเข้าพักได้ช้า และตรวจสอบย้อนหลังไม่ได้ว่าใครทำรายการใด

### 2.2 วัตถุประสงค์ทางธุรกิจ

| รหัส | วัตถุประสงค์ | ตัวชี้วัดความสำเร็จ |
|---|---|---|
| BO-1 | ขจัดการจองห้องซ้อนช่วงวัน | จำนวนการจองซ้อนในฐานข้อมูลเป็นศูนย์ตลอดเวลา (ตรวจด้วย Q13 ใน `queries.sql`) |
| BO-2 | ค้นหาห้องว่างและเสนอราคาได้ทันที | ค้นห้องว่างตามช่วงวันพร้อมราคาต่อคืนที่ถูกต้องตามแผนราคาในการเรียกครั้งเดียว |
| BO-3 | ยอดเงินของการจองถูกต้องและตรวจสอบได้ | ยอดรวม ยอดชำระ ยอดคืนเงิน และยอดคงค้างคำนวณจากข้อมูลต้นทางเสมอ ไม่มีการเก็บยอดซ้ำ |
| BO-4 | ห้องที่ขายได้ต้องพร้อมใช้งานจริง | ทุกการเช็คเอาท์สร้างงานทำความสะอาดครบทุกห้องโดยอัตโนมัติ และห้องที่แจ้งซ่อมถูกนำออกจากการขาย |
| BO-5 | ผู้บริหารเห็นรายได้และอัตราการเข้าพักแบบทันเวลา | รายงานรายได้ตามประเภทห้อง อัตราการเข้าพักรายเดือน รายได้รายวัน และการคาดการณ์ล่วงหน้า |
| BO-6 | ข้อมูลปลอดภัยและตรวจสอบย้อนหลังได้ | ทุกการเข้าสู่ระบบ การสร้างและเปลี่ยนสถานะการจอง และการแก้ไขข้อมูลสำคัญ มีบันทึกผู้กระทำและเวลา |

## 3. ผู้มีส่วนได้ส่วนเสียและบทบาทผู้ใช้

### 3.1 ผู้มีส่วนได้ส่วนเสีย

| ผู้มีส่วนได้ส่วนเสีย | ความสนใจหลัก |
|---|---|
| เจ้าของและผู้บริหารโรงแรม | รายได้ อัตราการเข้าพัก การกำหนดราคา ความถูกต้องของข้อมูล |
| ลูกค้า (ผู้เข้าพัก) | ค้นหาและจองห้องได้สะดวก ราคาโปร่งใส ยกเลิกหรือเลื่อนวันได้ตามนโยบาย |
| พนักงานต้อนรับส่วนหน้า | ทำรายการจอง เช็คอิน เช็คเอาท์ รับชำระเงิน และดูแลผู้เข้าพักได้รวดเร็ว |
| พนักงานแม่บ้าน | ทราบงานทำความสะอาดประจำวันและลำดับความสำคัญ |
| พนักงานบัญชี | ใบแจ้งหนี้ ภาษีมูลค่าเพิ่ม ยอดค้างชำระ และรายได้รายวัน |
| ผู้ดูแลระบบ | บัญชีผู้ใช้ สิทธิ์การใช้งาน และความปลอดภัยของระบบ |

### 3.2 บทบาทผู้ใช้ในระบบ

บทบาทผู้ใช้กำหนดโดย `app_user.role` ซึ่งมีค่าได้ 6 ค่าตาม CHECK constraint ส่วน `staff.role` มีค่าได้ 5 ค่า (ไม่มี `customer`)

| บทบาท (`app_user.role`) | ผู้ใช้ | หน้าที่หลัก |
|---|---|---|
| `customer` | ลูกค้าที่สมัครสมาชิกเว็บไซต์ | ค้นหาห้องว่าง จองห้อง เลือกบริการเสริม ชำระเงินออนไลน์ ดู ยกเลิก หรือเลื่อนวันการจองของตนเอง และรีวิวหลังเข้าพัก |
| `receptionist` | พนักงานต้อนรับส่วนหน้า | จองแทนลูกค้า เช็คอิน เช็คเอาท์ บันทึกไม่มาเข้าพัก รับชำระเงิน เพิ่มหรือลดรายการบริการ ออกใบแจ้งหนี้ ดูแลข้อมูลลูกค้า และเปลี่ยนสถานะห้อง |
| `housekeeping` | พนักงานแม่บ้าน | จัดการงานทำความสะอาด มอบหมายงาน และคัดกรองงานแจ้งซ่อม |
| `accounting` | พนักงานบัญชี | ดูและยกเลิก (void) ใบแจ้งหนี้ และดูรายได้ค่าห้องรายวัน |
| `manager` | ผู้จัดการโรงแรม | สิทธิ์ของงานส่วนหน้า แม่บ้าน และบัญชีทั้งหมด รวมถึงรายงานผู้บริหาร แผนราคา บริการเสริม ข้อมูลห้องและประเภทห้อง และประวัติการทำงาน |
| `admin` | ผู้ดูแลระบบ | สิทธิ์ทั้งหมดของผู้จัดการ และจัดการบัญชีผู้ใช้ บทบาท และประวัติการเข้าสู่ระบบ |

### 4.2 นอกขอบเขต

1. การตัดเงินผ่านช่องทางชำระเงินจริง (Payment Gateway) ระบบบันทึกการชำระเงินเป็นข้อมูลเท่านั้น
2. การส่งอีเมลหรือข้อความยืนยันการจอง
3. การเปลี่ยนห้องพักของการจองหลังสร้างรายการ (รองรับเฉพาะการเลื่อนวันโดยใช้ห้องเดิม)
4. การรับจองเกินจำนวนห้อง (Overbooking) และรายชื่อรอ (Waitlist)
5. การบริหารหลายสาขา (ระบบรองรับโรงแรมเดียว)
6. การกำหนดราคาแบบอัตโนมัติตามอุปสงค์ (Dynamic Pricing) นอกเหนือจากแผนราคาที่กำหนดล่วงหน้า
7. การเพิ่มหรือลบประเภทห้องผ่านหน้าจอ (ประเภทห้องแต่ละประเภทผูกกับเนื้อหาและภาพบนเว็บไซต์ จึงจัดการโดยผู้ดูแลฐานข้อมูล)

## 6. กฎทางธุรกิจ (Business Rules)

คอลัมน์ "การบังคับใช้" ระบุกลไกที่รับประกันกฎ: **DB** = ข้อจำกัดหรือทริกเกอร์ในฐานข้อมูล (ละเมิดไม่ได้แม้ติดต่อฐานข้อมูลโดยตรง), **App** = ตรวจสอบในชั้นแอปพลิเคชันก่อนบันทึก

### 6.1 การจองและห้องพัก

| รหัส | กฎทางธุรกิจ | การบังคับใช้ |
|---|---|---|
| BR-1 | อีเมลของลูกค้าต้องไม่ซ้ำกัน อีเมลของพนักงานต้องไม่ซ้ำกัน และชื่อผู้ใช้กับอีเมลของบัญชีผู้ใช้ต้องไม่ซ้ำกัน | DB: UNIQUE `customer.email`, `staff.email`, `app_user.username`, `app_user.email` |
| BR-2 | การจองหนึ่งรายการเป็นของลูกค้าหนึ่งคนเท่านั้น และต้องระบุพนักงานผู้รับผิดชอบหนึ่งคน การจองที่ลูกค้าทำเองทางเว็บไซต์บันทึกภายใต้พนักงานฝ่ายจองออนไลน์ | DB: `booking.customer_id`, `booking.staff_id` NOT NULL และ FOREIGN KEY; App: กำหนดพนักงานฝ่ายจองออนไลน์ |
| BR-3 | การจองหนึ่งรายการมีได้หลายห้อง (1 ถึง 10 ห้อง) และห้องเดียวกันห้ามปรากฏซ้ำในการจองเดียวกัน | DB: `uq_booking_room UNIQUE (booking_id, room_id)`; App: จำนวนห้อง 1-10 |

| BR-5 | ห้องหนึ่งห้องห้ามถูกจองซ้อนช่วงวันกับการจองอื่นที่ยังมีผล (สถานะ `pending`, `confirmed`, `checked_in`) โดยถือว่าช่วงวันซ้อนกันเมื่อ เช็คอินของรายการหนึ่ง < เช็คเอาท์ของอีกรายการ และ เช็คอินของอีกรายการ < เช็คเอาท์ของรายการแรก | DB: ทริกเกอร์ `bi_booking_room_no_overlap` (เมื่อเพิ่มหรือแก้ห้องของการจอง) และ `bu_booking_no_overlap` (เมื่อแก้วันที่หรือสถานะของการจอง) ทั้งสองใช้ advisory lock ต่อห้อง การจองห้องเดียวกันพร้อมกันจึงต้องรอกันและตรวจทีละรายการ; App: lock แถวห้องและตรวจล่วงหน้าเพื่อแจ้งผู้ใช้ (409) |
| BR-6 | ราคาห้องต่อคืนและราคาบริการเสริมต้องล็อกไว้ ณ เวลาที่ทำรายการ ใน `booking_room.price_per_night` และ `booking_service.unit_price` การเปลี่ยนราคาภายหลังไม่กระทบการจองเดิม ราคาห้องที่ล็อกคือราคาเฉลี่ยต่อคืนของช่วงเข้าพักตามแผนราคา | DB: คอลัมน์ราคาในตารางเชื่อม CHECK ≥ 0; App: คำนวณด้วย `fn_quote_stay` |

| BR-8 | สถานะการจองมี 5 ค่า และเปลี่ยนได้ตามลำดับนี้เท่านั้น: `pending → confirmed` เมื่อชำระครบ (การจองที่เคาน์เตอร์เริ่มที่ `confirmed`), `confirmed → checked_in` ได้ตั้งแต่วันเข้าพัก, `checked_in → checked_out`, และ `pending` หรือ `confirmed → cancelled` | DB: CHECK ค่าสถานะ; App: ควบคุมลำดับการเปลี่ยนสถานะ |

### 6.2 ยอดเงิน การชำระเงิน และรีวิว

## 9. ความต้องการที่ไม่ใช่เชิงหน้าที่ (Non-functional Requirements)

| รหัส | ด้าน | ข้อกำหนด |

| NFR-6 | ประสิทธิภาพ | มีดัชนีเสริม 28 รายการบนคีย์นอกและคอลัมน์ที่ค้นหาบ่อย ได้แก่ ช่วงวันเข้าพัก สถานะการจอง ห้องในการจอง การชำระเงิน แผนราคาที่เปิดใช้งาน กระดานงานแม่บ้าน งานซ่อมค้าง และเวลาของประวัติ รายการข้อมูลแบ่งหน้าได้สูงสุด 1,000 แถวต่อคำขอ |

| NFR-8 | การใช้งาน | ระบบรองรับภาษาไทยและภาษาอังกฤษทั้งส่วนลูกค้าและส่วนพนักงาน แสดงผลได้บนหน้าจอคอมพิวเตอร์และอุปกรณ์พกพา และมีสถานะระหว่างโหลดข้อมูล |

## 10. สมมติฐานและข้อจำกัด

1. ระบบรองรับโรงแรมเดียว สกุลเงินบาท (THB)
2. ราคาห้องและราคาบริการเป็นราคารวมภาษีมูลค่าเพิ่ม อัตราตั้งต้นร้อยละ 7
3. เวลาเช็คอินตั้งแต่ 15:00 น. และเช็คเอาท์ภายใน 12:00 น. วันเข้าพักพิจารณาเป็นวันตามปฏิทิน
4. วันหยุดสุดสัปดาห์สำหรับแผนราคา คือ วันเสาร์และวันอาทิตย์ (ISO day-of-week 6 และ 7)
5. การชำระเงินออนไลน์เป็นการจำลองเพื่อการศึกษา ไม่มีการตัดเงินจริง
6. ใบแจ้งหนี้ที่ถูกยกเลิก (void) ยังคงอยู่ในระบบเป็นหลักฐาน และการจองนั้นออกใบแจ้งหนี้ใหม่ได้ (partial unique index `uq_invoice_active_booking` จำกัดเฉพาะใบที่ไม่ void ให้มีได้ใบเดียว ตาม BR-18)
7. ระบบออกใบแจ้งหนี้ในสถานะ `issued` และยกเลิกเป็น `void` ยอดชำระและยอดคงเหลือของใบแจ้งหนี้คำนวณจากวิว `v_invoice_summary`
8. โครงสร้างฐานข้อมูลในเอกสารนี้เป็นฉบับสุดท้าย การพัฒนาต่อยอดต้องไม่เปลี่ยนโครงสร้างตาราง ข้อจำกัด วิว ฟังก์ชัน หรือทริกเกอร์
